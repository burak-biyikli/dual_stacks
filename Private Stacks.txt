LSU is a bottleneck in many applications due to the requirements of memory consistency


Stack is used for overflow of architectural state in addition for variables that may be used for interprocess communication


Because the stack uses the memory to have an unlimited size, it is also bound by the rules of the memory


Use of stacks in programs
* Function scoped variables
* Function stack frames
* Fills and Spills from architectural state
* Inter process communication


Disaggregation of the responsibility of stack accesses
* Separate shared process state from private thread state




Potential Benefits
* Reduced latency of stack operations
   * Similar in impact to Instruction Dependency Predictors (With stack access predictors) in addition to stack forwarding. Both can reach 0 cycle stack access latencies (push -> pop -> use). 
      * This becomes cheaper, as we unload the the IDP and handle this with a widget in rename
* Reduced use of limited LSU entries
   * Because we do not have commitments for multithreaded consistency, we do not need to actually perform loads and stores, saving entries in the LSU 
   * You still need infra to deal with private stack accesses, but this accounting is separate from the limited LSU. 
* Reduction of LD/ST bandwidth usage
   * Compared to aggressive latency reduction techniques, we also reduce the quantity of loads and stores required to complete the execution of kernels
   * Depending on the lifetime of pushes and pops, short lifetimes can be entirely elided while longer lifetimes are only deferred.
* Reduced cache usage
   * We can handle elements at the sub-cacheline granularity (Because stack accesses live in the PRF until evicted, and because having the CL is needed for consistency), so we no longer need to pull in cachelines from DRAM on a cold write to the stack just for correctness
      * Only true misses (e.g. lds from stores I have not done since context switch/drain) will be pulled in
   * Compared to aggressive latency reduction techniques, we save redundant cacheline usage
* Reduced coherence traffic and snooping
   * We do not need to CAM the cache for elements of the private stack
      * If the private stack is significant in size, we could save area by specializing ways of the cache
   * we do not need to track coherence at the cache line granularity
* Compilers can expose more parallelism
   * Graphs in parallel vs in series, spills and fills
   * Compiler (LLVM)  goes latency -> lifetime until high register. Could expose more ILP by staying in the latency mode
      * Reduced misprediction penalty as more ILP is exposed more quickly
   * Unrolling?
* Ability to trade register pressure for increased bandwidth in some workloads
   * Could have a widget that decides to evict private stack entries from the PRF depending on if a predictor thinks the workload is bandwidth or RF bound.
   * We could also have a Replacement policy that balances the desire to read and write full cachelines to the backing memory on eviction/miss with the different reuse potentials of cachelines.


Implementation Considerations
* Tracking of private stacks
   * Although the stack is thread private, we still need to deal with thread migrations and context switching. We need some way to transfer the memory backed private stack to a new core
      * Fine grain (Cacheline like) -> (Page like) -> (stack like)
   * The cache will need to deliver and hold the lines, but only a single copy of the line needs to be resident in the cache at once.
   * Ideally the private stacks are either entirely in the memory or partially in a single core
* OS involvement
   * Draining of the private stack by the OS can work in a time based way. E.g. after a drain instruction the ISA guarantees within X cycles the core will be drained of private stack entries. In a more limited form this is simply a hint instruction instead of core to correctness.
      * This is more relevant to maintain performance in a coarse grain tracking model
   * Draining of the private stack can be handled in a manner similar to cachelines, pulled in block by block
   * The OS and hardware  may need to jointly maintain a unique ID for each thread. This ID could be used to trigger a full drain in cores with private stacks that are not expected to be run again.
* Rolling flushes
   * The processor may speculate that certain stack entries are not likely to be used again, and preemptively drain them to the cache or main memory.


Pipeline impacts
* Decode
   * Detect accesses to the private and public stacks
* Rename
   * Assign names to stack accesses
   * Dispatch private stack accesses to the private stack pipes
* Memory Name
   * Stack position -> phys reg id OR phys addr 
* LSU
   * Effectively remove LSU entries for private stack accesses
   * Opportunistically drain private stack entries to memory for old entries or entries from other threads 
* TLB / MMU
   * Needs to handle coherence from context switch for coarse grain coherence method
* L1 Cache
   * Can be augmented into L1S 
   * L1S could have snooping insensitive ways to reduce area at the cost of reduced flexibility




Operating System Changes
* The operating system needs to be changed to give disjoint memory pages to each thread for the private stack. This would change several OS calls and the core kernel
* The operating system may need to change its context switching behavior depending on the synchronization method used by the private stack and private L1S cache
   * Now thread migrations are more expensive, as it leads to coherence traffic and startup latency
* Does the OS give a disjoint memory space to each private stack, or is the private stack in the same notional memory space? The ISA may allow peeks to the private stack, via explicit loads to the private stack pointer with offset if it is a new memory space. We could reuse the same memory space as well which would allow the emitted code to be more flexible. Essentially this is a strong versus weak typing problem


Compiler changes
* The compiler needs to determine if variables are visible between threads or not.
   * Does the compiler punt this problem to software via the use of keywords?
   * How does the compiler maintain backwards compatibility, do we need to explicitly mark both private and pubic? 
   * We could reuse some of the register promotion analysis the compiler does (If it can be a register it is private by definition)
* Unshared state can be placed in the private stack
* Atomics, and other Inter Process Communication need to be kept in the public stack
* Would require changes to multiple levels of the compiler stack like openmp

* Goals
   * Categorize stack accesses into Private, Strictly IPC, and Possibly IPC
   * Create a histogram of stack lifetimes
1. Cacheline granularity matching hardware patterns
2. Track stack accesses but compute every address
3. Make sure thread IDs to not overlap by assigning a tracking id per thread
4. consider a program where a function creates an atomic variable at the start of the function, then uses a threadpool to complete work. After this function we have a purely private kernel which spills to the stack. The first function with IPC might use SP_BASE + 1000 for the atomic, which then goes out of scope when the function is cleaned off the stack. The unrelated stack operations of the second function may be associated with a now out of scope IPC event. This behavior means that are tracking should be more  'live'. PCs for pushes/pops that are proven to be IPC will still be so between different spots of the control flow, but our conflict logic should disambiguate the two cases I mentioned. I think from the perspective of the L1 we would need to transition from shared -> unused on pop, and in the L2 we would need to trim/delete the structs as they leave scope
5. Determine the total number of ld/st/push/pop operations that occur during execution
   1. We will maintain a counter for each type of memory operation
   2. Pushes and pops will not show up in the ld/st count, to get the total operation count we will add all four counters.
6. Determine accesses/PCs of loads and stores that are associated with inter-process communication
   1. We can find the accesses that are hazarded by using a shadow memory with several states (unaccessed, last thread accessed, multithread accessed)
   2. We will keep track of what percent of stack accesses are ‘strictly interprocess’ and ‘interprocess’
      1. For strictly interprocess, if we had a load instruction at address 0x3000 which loaded addresses 0x1000, 0x1100, 0x1200, and another load instruction in another thread that loaded 0x1000 - then only the two loads to 0x1000 would be considered
      2. For interprocess, with the same example, every load done by address 0x3000 would be considered interprocess.
   3. Although loads and stores can create interprocess communication, and need to be tracked in the shadow memory for correctness, the stats are focused on pushes and pops to the stack
7. Determine the percentage of push/pop operations that are not strictly interprocess and not interprocess
   1. In the strict case, by examining the shadow memory, you might simply increment counters for each strictly interprocess push and pop. The complication comes where a push occurs then a load occurs to that address in another thread. The load operation needs to know how many stack operations to add to the counter, as 1 or more operations to that specific address may have occurred in the past
   2. In the interprocess case, we need to keep track of PCs that accessed memory addresses. One solution is to keep track of the pushes/pops performed at each pc. Each PC could be either in a count state or in a IPC state. When a non-IPC access occurs the counter is incremented (OR if we are in the IPC state, we increment the associated global counter. If the PC is involved in IPC we add the count for the PC to the global count, and transition state.
